# T-122 client／server 實際操作案例（全部待使用者執行）

共同條件：dedicated server＋兩個 client 使用同一包，從**新世界**開始，每次只改一種機制。先以 `/give` 取得 `simplerail:locomotive_cart`、`simplerail:wrench`、本模組軌道／發射器及原版礦車；在平坦處鋪連續軌道。可在 server console 執行 `data get entity <目標 UUID>`，或由 OP 以 `@e[type=simplerail:locomotive_cart,sort=nearest,limit=1]` 指定車頭；`/data get block x y z` 查方塊實體，`/execute if entity ...` 或 `/kill` **僅用於案例指明的清場**。每次記錄 server 與兩 client 的實體數／顯示、座標／時間；若有多台相近車頭，先移走其他測試車，避免 selector 指錯。

| ID | 操作步驟 | 事先預期 | 回報實際結果（目前待填） |
| --- | --- | --- | --- |
| T122-01 軌道回呼 | A 放普通礦車依序通過 `oneway_rail`、`holding_rail`、`timer_holding_rail`、`destory_rail`；B 旁觀。分別記有／無供電與狀態，必要時每軌重建新車。 | server 與兩 client 最終同一車數及方塊狀態；每次通過只有一份權威停止／移除。可見回饋不因兩 client 變成兩倍。具體時間依各軌既有驗收，不由本案虛定。 | 待使用者 |
| T122-02 扳手互動 | A 對可旋轉軌道、發射器與相鄰車頭／車廂各點擊一次；另讓 A、B 幾乎同時點同一目標一次，各自記方塊狀態、編組 `Train` 清單與粒子／聲音。 | 單次操作不在 client 先改權威狀態；每一個實際 server 接受的操作只寫一次。重複 link 不產生同 UUID 兩節；兩人各自一次點擊可形成兩個有效操作，不能把它誤判為「重複執行」。 | 待使用者 |
| T122-03 手持車頭 | A 在南北、東西軌道各放一台車頭；記放置前後物品數。B 在場及稍後重連，再核對 server `UUID`／`Facing`、兩 client 顯示與車數。 | 每次成功放置只生成一台且只扣一件，UUID 一致；東西向初始朝向與兩端一致。 | 待使用者 |
| T122-04 發射器 | 以發射器的 27 格 GUI 設第 0 格車頭、第 1 格普通礦車；記樣板數量。提供一次紅石鄰居更新，A／B 同時觀察；再以第 1 格車頭、第 0 格空格做獨立測試。 | 每次確實收到的 server 事件只按樣板規則生成；樣板不耗用。第 0 格頭才能接管原版車；其他格頭可生成但不接管。實際鄰居事件次數與生成次數分開記，不把多次事件當成 client 重複。 | 待使用者 |
| T122-05 朝向與追蹤 | A 在東西向軌道放車頭，靜止時立即記 server `Facing` 和 A／B 畫面；推車沿東、西、南、北及可達斜向行進後停止，再讓 B 離開追蹤範圍並重連。 | server 朝向為權威，兩端最終一致；首次顯示及重連不保留舊方向。若無法可靠看到首幀，明列「首幀待確認」，不要寫通過。 | 待使用者 |
| T122-06 刪除 | 用扳手建立一頭兩車，記三個 UUID；讓車頭通過有作用的 `destory_rail`；另以無關車及未供電且需供電設定作對照。 | 只刪目標整列；server、A、B 不殘留幽靈車或重複煙霧／聲音，無關車保留。若另測車廂卸載後刪頭，重載該區塊後車廂亦不應復活；記區塊載入順序。 | 待使用者 |
| T122-07 GUI／計時 | A 開發射器 GUI 改一槽，B 接著開同一 GUI；兩端關閉重開。讓普通車進計時軌，在約剩 3 秒時卸載／關服再讀回，B 旁觀。 | GUI 與 server BE 槽位一致，沒有 client-only 物品；計時依 D5 卸載／離線暫停，重載後仍約需 3 秒。容許誤差待技術定義；無法量測時標待確認。 | 待使用者 |

結果分類可用「通過／發現問題／條件不足」。只由使用者提供實際現象；建議附任務／案例 ID、受測 JAR SHA-256、server／A／B log 相關時間段及可辨識 UUID 的截圖，但使用者直接文字確認即可。OLD 的未實測行為均為「依原始碼推定／待確認」，不能把本包 NEW 結果寫成 OLD 基線。
